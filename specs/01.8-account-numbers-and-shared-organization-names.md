# 01.8: Account numbers and shared organization names

- **Status**: Implemented (approved 2026-09-26)
- **Protocol**: Corporate Standard chapter 7 (inventory quality management: the
  reporting entity is identified without ambiguity), chapter 9 (reporting: the
  report names the company it describes), ISO 14064-1 section 8 (records)
- **Owner**: Michael Takrama
- **Created**: 2026-09-26
- **Modules**: `ghg` (organizations, the report, the PDF, the export, the
  platform summary, the factor-pack impact report), `src/features/ghg`,
  `src/features/admin`

## Problem

Two clients can legitimately carry the same name: a group and its trading
company, a franchise, a client onboarded a second time while its first
organization still stands. Spec 02 made the name unique among live
organizations (case-insensitive) and spec 01.3 kept that rule as a partial
unique index, so the second client is refused with "An organization named
'X' already exists." and cannot proceed at all.

The name is also the only identity a person can read. The UUID in the URL is
not a thing anyone reads off a PDF or says on a support call, and nothing on a
list, a switcher, a report or a banner would tell two organizations of one
name apart if the rule were simply dropped.

## Behavior

### The account number

- Every organization carries an **account number**: a positive integer taken
  from one platform-wide sequence when the organization is created. It is
  assigned once, in creation order, never changed and never reused. A removed
  organization (spec 01.3) keeps its number.
- It is displayed as `ORG-` followed by the number padded to four digits
  (`ORG-0042`), and wider once it outgrows them (`ORG-10000`).
- The sequence guarantees uniqueness and order, not contiguity: a creation
  that fails after the number is taken leaves a gap, and that is fine. The
  number is taken after every check the creation makes, so a refusal takes
  none.
- Organizations that existed before this spec are numbered in creation order
  when the migration runs, tombstones included.

### Shared names: warn, then allow

- Two live organizations **may** share a name. The name is compared trimmed
  and without regard to case, as before.
- Creating an organization, or renaming one, into a name another live
  organization carries is **refused once**: the response names each such
  organization with its account number and says how to proceed. Re-sending
  the same request with `allowDuplicateName` set proceeds. The client shows
  the refusal beside the form and turns the submit control into **Create
  anyway** or **Save anyway**; changing the name withdraws the confirmation.
- A removed organization never counts as a duplicate. An organization is
  never a duplicate of itself: alone with its name, a change of case alone
  passes; when another organization carries the name, even a change of case
  is refused once like any other rename into that name.
- A refused creation must not take an account number.

### Where the number appears

The account number appears beside the name wherever the name appears: the
organization list cards, the organization switcher, the settings page header,
the platform administrators' organizations table and their **Assume access**
dialog, the support-access banner, the dashboard's privileged-access
register, the factor-pack impact report, the run page header, section 1 of
the report and its **Reporting entity** row, the PDF title, header row and
footer, the PDF file name, and the toasts that confirm a creation, a save or
a deletion. Deleting an organization still takes the name typed exactly
(spec 01.3); the dialog states the account number so the owner knows which
of two same-named organizations they are removing.

### The rename in the history

A rename is recorded in the organization's history (spec 01.7) as
**Organization renamed**, with the old and the new name. When the rename
needed the confirmation, the reason also names each organization it now
shares the name with. Saving the details without changing the name records
nothing; a change of case alone is a rename.

Given Ama creates "Adansi Foods Ltd" as the first organization on the
deployment: it is ORG-0001, the toast reads "Adansi Foods Ltd (ORG-0001)
created." and the card carries the number. When Kofi creates "adansi foods
ltd", the form refuses once: "An organization named 'adansi foods ltd'
already exists: Adansi Foods Ltd (ORG-0001). Confirm to use the name
anyway." with the button now reading **Create anyway**. When he clicks it,
ORG-0002 is created. The switcher lists "Adansi Foods Ltd (ORG-0001)" and
"adansi foods ltd (ORG-0002)". When Kofi renames ORG-0002 to "Adansi Foods
Ltd" with **Save anyway**, its history reads "renamed from 'adansi foods ltd'
to 'Adansi Foods Ltd'; shares the name with ORG-0001". When he deletes
ORG-0002 by typing its name, the next organization anyone creates is
ORG-0003, and creating "Adansi Foods Ltd" again is still refused once,
because ORG-0001 is live; the tombstone does not count.

## API

- `OrganizationResponse` and `AdminOrganizationResponse` gain `accountNo`
  (integer).
- `POST /organizations` and `PUT /organizations/{id}` accept an optional
  boolean `allowDuplicateName` (absent means false).
- 409 `Duplicate organization name` when another live organization carries
  the name and the flag is not set:

  ```json
  {"type": "about:blank", "title": "Duplicate organization name", "status": 409,
   "detail": "An organization named 'adansi foods ltd' already exists: Adansi Foods Ltd (ORG-0001). Confirm to use the name anyway.",
   "instance": "/api/ghg/organizations",
   "duplicates": [{"id": "…", "name": "Adansi Foods Ltd", "accountNo": 1}]}
  ```

  It is a 409 rather than a 422 because it is a refusal about state that
  must carry the list of organizations; the client detects the case by the
  `duplicates` property, never by the status alone. This is the product's
  first warn-then-allow refusal; the pattern is recorded in
  `docs/reference/conventions.md`.
- `ReportResponse.header` and `ReportResponse.company` gain
  `organizationAccountNo`. The PDF prints the name and the number together
  in its title, footer, **Reporting entity** row and section 1.
- `GET /runs/{id}/report.pdf` is named
  `<organization slug>-org-<nnnn>-<period slug>-run-<n>.pdf`
  (`adansi-foods-ltd-org-0001-fy2025-run-1.pdf`), so two organizations'
  reports never collide on disk. Spec 07.5 is amended.
- `PlatformSummaryResponse.grants[]` gains `organizationAccountNo`, null
  when the organization has since been removed. The factor-pack impact
  report's `organizations[]` gains `organizationAccountNo`, and two holders
  of one name sort by it.
- `AuditEventResponse.action` gains `ORGANIZATION_RENAMED`.
- `DELETE /organizations/{id}` is unchanged.

## Data

`V56__organization_account_numbers.sql`:

- `ghg_organizations_account_no_seq`, a bigint sequence owned by the new
  column.
- `ghg_organizations.account_no bigint NOT NULL UNIQUE CHECK (> 0) DEFAULT
  nextval(...)`, backfilled over every row, tombstones included, in
  `created_at` order (ties broken on `id`); the sequence is then set past the
  highest number. The service takes the number explicitly with `nextval`
  after every check; the default is a safety net for ad hoc SQL.
- `uq_ghg_organizations_live_name` is dropped and replaced by a non-unique
  partial index `idx_ghg_organizations_live_name` on `lower(name)` where
  `deleted_at IS NULL`, for the duplicate lookup. Spec 01.3's partial unique
  index is superseded here.
- `ghg_audit_events` action check gains `ORGANIZATION_RENAMED`.

## Non-goals and open questions

- The account number is not editable, not prefixed per tenant, and not
  searchable. Searching the administrators' table and the switcher by number
  is the likely first request from support; a later spec.
- Record numbers (spec 04.6) and run numbers (spec 05.2) stay per
  organization; the account number is the only platform-wide one.
- Rule refusals inside an organization ("'X' needs at least one owner.",
  "is already a member of 'X'") and the reporting-company legal entity's
  name keep the bare name: inside an organization there is only one.
- The dashboard's grant register reads "a removed organization" for a
  tombstone, as before; showing the retained number there is a small
  follow-up.
