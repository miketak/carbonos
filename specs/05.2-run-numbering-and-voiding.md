# 05.2: Run numbering and voiding

- **Status**: Implemented
- **Protocol**: Chapter 7 (inventory quality management), Chapter 9
  (transparency), ISO 14064-1:2018 section 8.2 (records)
- **Owner**: Michael Takrama
- **Created**: 2026-09-09 (audit finding F35, ticket T-05); implemented
  2026-09-09
- **Modules**: `ghg` (`GhgRun`, `GhgAuditEvent`, the run endpoints),
  `src/features/ghg` (runs list, lifecycle bar)

## Problem

Spec 05.1 describes runs as immutable snapshots, yet a run could be deleted
with one click: no confirmation, no reason, no trace. The next run was
numbered 001 again, so the history did not even show that a run had existed,
and a run marked FINAL could be deleted until publication. A verifier who
learns that runs can be silently deleted and renumbered will not rely on any
run history.

## Behavior

- **Numbers.** Every run of an inventory carries a **run number** the server
  assigns: one more than the highest number the inventory has ever issued,
  voided runs included. Numbers are never reused. The page proposes the
  label "Run NNN" from the next number and prints the number beside the
  label.
- **Voiding replaces deletion.** A run cannot be deleted. It can be
  **voided** with a required reason (5 to 500 characters). A voided run
  stays listed with its number, its figures, the reason, who voided it and
  when; its report opens with a VOIDED banner. A voided run cannot be
  designated final and cannot be cited as a recalculated base (spec 06.1).
  Voiding is refused on a published inventory.
- **A FINAL run is protected.** Voiding the final run is refused; the
  designation must be withdrawn first, and withdrawing it now requires a
  reason. Both the withdrawal and the void are recorded as audit events.
- **Audit events.** `ghg_audit_events` records, per inventory: the action
  (`RUN_VOIDED`, `FINAL_WITHDRAWN`), the run, the actor's id and email, the
  reason, and the time. The inventory page lists them under "History". Later
  specs extend the list to classification, freeze, final, publish and
  correction (ticket T-22).

Given inventory A with runs 001 and 002, when the accountant voids run 001
with the reason "boundary v1 omitted the Nkran camp", then the runs list
shows 001 as VOIDED with the reason and 002 as before, and the next run is
numbered 003.

## API

- `POST /runs/{id}/void` `{reason}` → `RunResponse`; 409 when the run is
  final, already voided, or on a published inventory; 422 without a reason.
- `DELETE /runs/{id}` is gone (405).
- `POST /inventories/{id}/withdraw-final` takes `{reason}` (422 without
  one).
- `RunResponse` gains `runNo`, `voided`, `voidedAt`, `voidedBy` and
  `voidReason`.
- `GET /inventories/{id}/events` → `{action, runId, runNo, actor, reason,
  at}[]`, newest first.

## Data

`V22__run_numbering_and_voiding.sql`: `run_no` on `ghg_runs` (unique per
inventory, backfilled in creation order), `voided_at`, `voided_by_user_id`,
`voided_by`, `void_reason`; `ghg_audit_events` (inventory, run, action,
actor id and email, reason, created_at).

## Non-goals and open questions

- Un-voiding a run. A voided run stays voided; the accountant launches a
  new one.
- Voiding runs of a published inventory. The published record stands; a
  correction supersedes it (spec 05.1).
