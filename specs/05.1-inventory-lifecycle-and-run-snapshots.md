# 05.1: Inventory lifecycle and run snapshots

- **Status**: Draft
- **Protocol**: Chapter 7 (inventory quality management), Chapter 9
  (exclusions reported with justification), Chapter 10 (verification)
- **Owner**: Michael Takrama
- **Created**: 2026-09-02
- **Modules**: `ghg`, `src/features/ghg`

## Problem

Spec 03 made the boundary reproducible. Two gaps remain with one root cause:
the inventory itself has no lifecycle, so its parts are governed piecemeal.

First, the activity view is not reproducible. A run snapshots the lines it
calculated, but an *excluded* assignment leaves no trace, and included ones
can be reclassified after the run. Chapter 9 requires exclusions to be reported
with justification, and a verifier (Chapter 10) audits completeness; neither
can be reconstructed for a past run.

Second, a run can be designated final while the boundary is later reopened,
changed and re-frozen, so the inventory's current boundary can differ from its
final report's. The Standard frames the boundary as a declaration for a
reporting period, which puts the lifecycle on the inventory. And a 0%-share
facility is today a boundary member "contributing nothing"; in the Standard's
terms it is outside the boundary under that approach.

## Behaviour

- **Inventory states.** `DRAFT`: boundary and activity view editable, runs
  blocked. `FROZEN`: both halves read-only, runs allowed. `FINAL`: a run is
  designated final; reopening is refused until the designation is withdrawn.
  `PUBLISHED`: a report was issued; nothing may change, and a correction is a
  new inventory that supersedes this one. Freezing becomes one act covering
  both halves; spec 03's boundary status folds into the inventory status.
- **Complete snapshots.** A run records every assignment that existed when it
  was launched: included ones as lines (today), excluded ones as exclusion
  records carrying the activity's facts and the documented reason. The report
  lists exclusions under the lines, grouped by reason.
- **Zero-share facilities** are represented as outside the boundary under that
  approach: the gate offers to remove them, and versions record them as
  excluded with the reason rather than as members at 0%.
- In any state but `DRAFT`, classify, exclude, include and boundary writes are
  refused with 409, as boundary writes are today.

Given inventory A frozen and its run designated final, when a user tries to
reopen the boundary, then the request is refused until the final designation is
withdrawn; when they withdraw it, reopen, change Tarkwa, re-freeze and run
again, the earlier run still cites v1 and lists the exclusions as they stood.

## API

`POST /inventories/{id}/freeze`, `/reopen`, `/finalize`, `/publish`,
`/supersede`; `RunDetailResponse` gains `exclusions[]`; 409 `Operation not
allowed` on writes the state forbids.

## Data

`ghg_inventories.status` replaces `boundary_status`; `superseded_by_id`; new
`ghg_run_exclusions` denormalizing the activity facts and reason as
`ghg_run_lines` does. Boundary versions become one part of an inventory version.

## Events

`InventoryPublished(inventoryId, runId)` for future reporting and notification
consumers.

## Verification

Integration tests per transition and per refused write; a run's exclusion
list survives later reclassification; the QA scenario's ANFO exclusion appears
in the report.

## Non-goals and open questions

A preparer/approver workflow with separate roles needs multi-member
organizations (spec 01 non-goal). Diffing two runs' exclusion sets. Whether
reopening under `FINAL` requires withdrawing the designation first (recommended)
or is refused outright.
