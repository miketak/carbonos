# 01.1: Access requests

- **Status**: Implemented
- **Protocol**: none; the self-service branch of getting in
- **Owner**: Michael Takrama
- **Created**: 2026-08-29
- **Modules**: `user` (requests, approval, account setup), `mail` (outbound
  email), `src/features/access`, `src/features/admin`, `src/features/home`

## Problem

Without this, accounts exist only when an administrator creates them (spec 01)
or the seed variables do. A prospective user on the public landing page needs
a path in that ends with an administrator's decision.

## Behaviour

1. **Request.** On the landing page a visitor clicks *Request access* and
   submits name, email and optionally a company. The system stores a `PENDING`
   request and shows a confirmation. An email that already belongs to a user,
   or already has a pending request, is refused with 409; the message does not
   reveal which.
2. **Queue.** Administrators see requests (name, email, company, requested
   date), newest first, with Approve and Deny.
3. **Approve.** The request becomes `APPROVED`, receives a single-use setup
   token valid for 7 days, and the requester is emailed
   `{APP_BASE_URL}/set-password?token=…`. The email comes from the configured
   sender and is addressed to the requester by name.
4. **Set password.** The link opens a form showing the requester's email.
   A valid password (8 to 72 characters, entered twice) creates an `ACTIVE`
   `MEMBER`, consumes the token (request becomes `COMPLETED`), signs the user in
   and lands on `/app`. Unknown, used and expired tokens all show the same
   "link invalid or expired" state (404) with a way back to the landing page.
5. **Deny.** The request becomes `DENIED` and a polite decline is emailed. A
   denied address may request again later.

Decisions recorded at implementation: emails go out asynchronously through a
Spring Modulith event listener (at-least-once, retried from the event registry
on restart); if the email gains an account before the link is used, completion
fails with 409; completion signs the user in directly, with no second trip
through the login form.

## API

Public (CSRF token still required on POSTs):

- `POST /api/access-requests` `{email, displayName, company?}` → 202; 409
  `Duplicate request`; 422.
- `GET /api/access-requests/setup/{token}` → 200 `{email, displayName}`; 404
  `Invalid or expired link`, non-enumerating.
- `POST /api/access-requests/complete` `{token, password}` → 200 user plus
  session; 404; 409 if the email now has an account; 422.

Administrator (`/api/admin/**`):

- `GET /api/admin/access-requests` → all requests, newest first.
- `POST /api/admin/access-requests/{id}/approve` and `/deny` → 200; 409
  `Operation not allowed` when not `PENDING`; 404.

## Data

`V5__access_requests.sql`: `access_requests(id, email, display_name, company,
status CHECK IN (PENDING, APPROVED, DENIED, COMPLETED), setup_token unique,
token_expires_at, decided_at, decided_by → users ON DELETE SET NULL, created_at,
updated_at)`. A partial unique index on `email WHERE status = 'PENDING'` allows
one open request per address. Tokens are 64 hex characters from `SecureRandom`.
Decided requests are retained as audit trail; there is no purge yet.

## Events

Published by `user`, consumed by `mail`: `AccessRequestApproved(requestId,
email, displayName, setupToken)` and `AccessRequestDenied(requestId, email,
displayName)`. `mail` renders plain-text messages over SMTP (`spring.mail.*`;
Mailpit locally and in tests). `carbonos.mail.from` and `carbonos.app.base-url`
configure the sender and link base and must be set on every deployment.

## Verification

## Non-goals and open questions

Password reset for existing users (a natural reuse of the token mechanism);
rate limiting or CAPTCHA on the public form; HTML email; administrator
notification of new requests; a retention policy for old requests.
