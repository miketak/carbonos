# 02.6: Versioned pack import: a factor's lineage and its vintages

- **Status**: Approved (2026-09-13)
- **Protocol**: Chapter 1 (consistency: one factor set applied the same way
  across an inventory and across years), Chapter 9 (the factors used and
  their sources are reported), ISO 14064-1:2018 clause 8.2 (records are
  retained). Chapter 5 asks whether a changed factor triggers a base-year
  recalculation; spec 02.7 owns that question.
- **Owner**: Michael Takrama
- **Created**: 2026-09-13
- **Modules**: `ghg` (`FactorPackImportService`, `GhgService`,
  `EmissionFactor`, `InventoryAssignmentRepository`, `GhgRunLineRepository`),
  `src/features/ghg` (emission factors page, classification picker)

## Problem

Importing a pack overwrites. `GhgService.importPack` keys on the publication
row identifier and calls `current.update(...)` on a row the organization
already holds, replacing its name, scope, category, unit, CO2e per unit,
every gas component, its blend, and its provenance. Only the approval flag
survives. A maintainer who corrects a factor therefore changes a client's
numbers on the client's next import, with no record that a number moved and
no way to state which vintage an inventory used. Chapter 1 asks for one
factor set consistently applied and clause 8.2 asks for the record of what
was applied. An overwrite keeps neither.

Three defects make it worse today:

- Every import writes null into a factor's validity. The provenance is built
  as `new EmissionFactor.Provenance(citation, url, year, dataYear, null,
  null, notes)` and `EmissionFactor.update` assigns both, so a factor a
  preparer retired by setting `valid_to` is silently returned to service.
- A row whose unit the registry cannot convert is skipped with a bare
  `continue`. Nothing counts it and nothing tells the caller, so a pack can
  deliver fewer factors than it lists without saying so.
- Deleting a factor a classification uses relies on the bare foreign key
  `emission_factor_id uuid NOT NULL REFERENCES ghg_emission_factors (id)`
  from `V4__ghg_accounting.sql`. `GhgService.deleteEmissionFactor` guards
  only against run lines, so the violation reaches the generic handler and
  the caller gets 500 instead of a refusal naming the inventory.

## Behavior

### A code is a lineage, not a row

The publication row identifier is a **lineage key**. A lineage holds one
version per vintage, and a factor's identity is the organization, the
`pack_code`, and the version's `valid_from`.

Existing rows keep a null `valid_from`, which means the version has always
applied. That is what `EmissionFactor.coversPeriod` already implements: a
null start covers every period. `valid_from` is not backfilled on rows an
organization already holds. Backfilling it to an edition's first day would
stop those versions covering earlier periods, and the two organizations
holding 317 pack-derived factors would see coverage warnings on inventories
that were clean the day before. A record must not change because the product
changed.

### Importing an edition

Given a published edition with an `applies_from` date, the import walks its
rows in order and never mutates a value on an incumbent version.

1. **A locked period refuses the whole import.** While `applies_from` falls
   inside the period of any inventory of the organization whose status is
   `FROZEN`, `FINAL`, or `PUBLISHED`, the import returns 409 naming that
   inventory and its status, and writes nothing. A reported period keeps the
   factors it reported with.
2. **A unit the registry cannot convert is reported.** The row is not
   imported. Its code and unit are carried back, so the caller learns what
   the edition could not deliver.
3. **A lineage the organization does not hold is created**, with
   `valid_from` set to `applies_from` and `valid_to` null.
4. **A locally edited version is never touched.** The row is left as it is
   and its code is carried back as a **conflict** for a person to resolve.
5. **The same edition is idempotent.** When the live version already records
   this edition, the import ensures the tag is present and changes nothing
   else. Re-importing is a no-op, not a version bump.
6. **Identical values only gain a tag.** When the live version came from
   another edition but every value matches, the import adds the tag and
   records the edition. No version is cut, because there is nothing to
   distinguish.
7. **Anything else cuts a version.** The incumbent's `valid_to` becomes the
   day before `applies_from`, and only when its current `valid_to` is null or
   later, so an earlier retirement is never extended. A new version is
   inserted with the edition's values, `valid_from` set to `applies_from`,
   and `valid_to` null. Where `applies_from` falls inside the period of an
   open draft inventory, the affected inventory is carried back as
   `splitPeriods`, because one reporting year calculated on two editions
   breaks the consistency principle of chapter 1; the decider is told before
   accepting and the run discloses both editions.

Approval carries forward from the incumbent, because approval is a decision
the organization made about the lineage. An edition row that is itself
unapproved, such as a supplier template, produces an unapproved version.
Local edits do not carry forward: a version carries the edition's values or
it is not that edition's version. The edition row's `source_category`,
`source_activity`, and `source_detail`, which spec 02.5 defines, are carried
onto every version the import creates.

A lineage the organization holds under the predecessor that the new edition
does not contain is reported as **discontinued**. The import retires nothing.
A publisher dropping a row is a decision for the organization, and silent
retirement would move a number without anyone saying so.

### Retirement, never deletion

A pack-derived factor is never deleted. It retires by setting `valid_to`, and
its versions stay on file. A hand-entered factor with no pack code, no run
line, and no classification can still be deleted.

Given a factor a classification uses, when a user deletes it, then the API
refuses with 409 naming the inventory that classified with it. Given a factor
a run applied, the refusal names the run, as it does today.

### What versioning does not touch

A run is a snapshot. `ghg_run_lines.factor_id` and `ghg_run_factors.factor_id`
are plain identifiers with no foreign key, and the run records the name,
values, provenance, tags, and the `source_edition` and `valid_from` of the
version it applied, so every reported figure names the edition behind it as
ISO 14064-1:2018 clause 9.3.1 requires. Cutting a version cannot reach a
past run.

Given a published inventory whose run applied version 1 of a lineage, when
the organization imports a later edition and version 2 is cut, then the
published report still prints version 1's value, its source, and its year.

### A visible change to disclose

A version cut by an import carries a real `valid_from` for the first time.
An organization that adopts an edition and then runs an **earlier** period
sees a coverage warning the same inventory did not raise before, because the
version it would apply does not cover that period. The warning is correct and
it is the point of a vintage. The emission factors page lists each lineage's
versions with their validity, so a preparer can see which vintage applies.

## API

- `POST /organizations/{organizationId}/factor-packs/{editionId}/import`
  keeps its path and the write set that spec 01.4 already places **Import
  pack** in, so `access.checkWrite` still guards it. Running an import is a
  preparer's act. Deciding that a published edition becomes this
  organization's vintage is not, and spec 02.7 reserves that to a reviewer or
  an owner.

  The result widens, and its first field is renamed. `ImportResult.pack`
  becomes `edition`, because a pack family now has many editions and the
  result names the one that was imported. The frontend interface
  `FactorPackImport` follows the rename:

  ```json
  {
    "edition": "defra-2026",
    "appliesFrom": "2026-01-01",
    "created": 12,
    "versioned": 340,
    "tagged": 4,
    "unchanged": 1512,
    "skippedUnits": [{ "code": "DEFRA:...", "unit": "MJ" }],
    "conflicts": ["DEFRA:Fuels:..."],
    "discontinued": ["DEFRA:Retired_row:..."],
    "splitPeriods": [{ "inventoryId": "...", "name": "2026 Corporate" }]
  }
  ```

- 409 `GhgRuleViolationException` when `applies_from` falls inside a locked
  period, with the detail naming the inventory and its status.
- 409 when a delete targets a pack-derived factor, a factor a run applied, or
  a factor a classification uses, each naming what holds it.
- 404 `GhgNotFoundException.pack(editionId)` for an edition that is not
  published, as spec 02.5 defines visibility.
- `EmissionFactorResponse` gains `sourceEdition`, `locallyEdited`,
  `validFrom`, `validTo`, and the lineage's other versions, so the page can
  show the chain.

## Data

One migration belongs to this spec. `V46__run_factor_edition.sql` adds
`source_edition` and `valid_from` to `ghg_run_factors`, backfilled null for
runs made before versioning, so a past run reads as unknown rather than
being credited to an edition it never saw. Number assigned in the planned
implementation order; renumber if that order changes.

The other columns and the index this spec relies on ship with spec 02.5's
`V42__factor_pack_editions.sql`:

- `source_edition`, `locally_edited`, and `superseded_by_id` on
  `ghg_emission_factors`.
- `source_category`, `source_activity`, and `source_detail` on
  `ghg_emission_factors`, backfilled from the edition row by `pack_code`.
  A row whose code matches no edition row keeps nulls.
- `idx_ghg_emission_factors_pack_code`, created by
  `V38__factor_identity_across_packs.sql` as
  `(organization_id, pack_code) WHERE pack_code IS NOT NULL`, becomes
  `(organization_id, pack_code, valid_from) NULLS NOT DISTINCT WHERE
  pack_code IS NOT NULL`. `NULLS NOT DISTINCT` keeps at most one open-start
  version per lineage, so existing rows stay legal and stay unique.

`chk_ghg_emission_factors_validity` from `V27__emission_factor_library.sql`
still holds: a version's `valid_from` never follows its `valid_to`. The three
defect fixes need no schema change and ship before the rest.

`RunFactorResponse` and the frozen-inputs export of spec 07.5 carry the two
new columns, so the factor table of a report names the edition and the
vintage behind every line.

The import truncates a citation longer than 500 characters to fit
`ghg_emission_factors.source`, which stays `varchar(500)`. The truncation
moves with the code into `FactorPackImportService` and stays a guard on that
column rather than an artifact of the old JSON. It is a backstop: an edition
row whose citation would not fit is a validation failure under spec 02.5, so
a published edition never relies on it.

## Non-goals and open questions

- The edition lifecycle, the authoring console, the validation rules, the
  publication gate, and the seeding of the ten shipped editions: spec 02.5.
- The notice, the diff, the named decision, and the recalculation question
  that follow a publication: spec 02.7. This spec describes what an import
  does once a person has decided to run it.
- Server-side filtering and pagination of the factor picker, which the
  version chain makes longer: the picker phase of the same plan.
- Merging two lineages, or moving a version from one lineage to another. A
  code never changes, because it is the identity of rows organizations
  already hold.
- Automatic adoption of a new edition stays a non-goal, as spec 02.1 states.
