# 01.10: Date format preference

- **Status**: Approved (the owner agreed the decisions on 2026-10-07)
- **Protocol**: none directly; Corporate Standard chapter 7 (inventory quality
  management) and ISO 14064-1 section 8 (records) need dates a reader cannot
  misread
- **Owner**: Michael Takrama
- **Created**: 2026-10-07
- **Modules**: `user` (the preference, the profile endpoint, the public
  lookup), `ghg` (the calculation and evidence CSVs), `src/lib/dates.ts`,
  `src/features/profile`, every feature that prints a date

## Problem

A reader in the United States writes 3 April 2026 as 04/03/2026; a reader in
Ghana writes it 03/04/2026. Each reads the other's form as a different day.
CarbonOS has no setting for this and no single place that formats a date:
about thirty screens call the browser's default formatter, the register
builds `2026-09-11 08:11` by hand, the help centre hard-codes British
English, and several pages print the stored ISO value as it is. The same
person sees three forms in one session, and none of them is the one they
chose.

Stored and typed data is not at risk. Every date field is a native date
input, which the browser already shows in the operating system's form and
sends as ISO; every import parses ISO only (spec 04.11, "the template is the
contract"). What changes is what people see and download.

## Behavior

### The preference

- Each account carries a **date format**: `DMY` (day/month/year) or `MDY`
  (month/day/year), or none chosen yet.
- While none is chosen, the app follows the browser's locale: a browser that
  puts the month first gets `MDY`, every other browser gets `DMY`.
- The profile page (spec 01.9) gains a **Preferences** section with the
  select **Date format** and the options "Day/Month/Year (31/12/2026)" and
  "Month/Day/Year (12/31/2026)". A change saves at once and the toast reads
  "Preferences updated". Every screen that prints a date follows the new
  choice without a reload.

### What follows the preference

- Every date the product prints on screen: `DD/MM/YYYY` or `MM/DD/YYYY`. A
  date with a time appends ` HH:mm` (24-hour) in the viewer's time zone, so a
  register entry reads `03/04/2026 08:11` or `04/03/2026 08:11`.
- A month on its own keeps the written form, "Aug 2026", which is
  unambiguous in both conventions.
- The calculation file and the exclusions file of a run (spec 07.5) and the
  evidence index (spec 04.6): the `period_start`, `period_end` and
  `uploaded_at` columns carry the downloader's form. An account with no
  choice yet downloads ISO, as before. The run files therefore vary between
  downloaders in those columns only; the row count, the order and every
  number stay the same, which is what a verifier re-performs.

### What does not

- The report PDF and every email keep the written month, "7 October 2026",
  which both conventions read the same way.
- Date inputs stay native; the browser already localizes them.
- Imports accept ISO only. `03/04/2025` in a spreadsheet cannot be read
  safely, and the template's example row and the rejection sentence "is not
  a date (use 2025-03-31)" are unchanged.
- The frozen inputs JSON (spec 07.5) stays ISO: it is for machines.

## API

- `GET /api/profile` and `GET /api/auth/me` carry `dateFormat`: `"DMY"`,
  `"MDY"` or `null`.
- `PUT /api/profile/preferences` with `{"dateFormat": "DMY" | "MDY"}` answers
  200 with the profile. A missing value is 422 with "Choose a date format."
  on `dateFormat`; an unknown value is 422 with the reader's message.
- `GET /api/ghg/runs/{id}/lines.csv`, `.../exclusions.csv` and
  `GET /api/ghg/organizations/{id}/evidence/index.csv` format their date
  columns by the caller's preference.

## Data

- `V68__user_date_format.sql`: `users.date_format varchar(3)`, nullable, with
  a check on `DMY` and `MDY`. No backfill: null is "not chosen yet".
- `UserDirectory.UserSummary` (the user module's public lookup) gains
  `dateFormat`, so the `ghg` module reads the preference without touching
  the user module's internals.

- `ProfileApiIntegrationTests`: the preference round-trips through
  `PUT /api/profile/preferences`, `GET /api/profile` and `GET /api/auth/me`;

- `RunCsvTests`: the period columns read `03/04/2026` under `DMY`,

- `src/lib/dates.test.ts`: `2026-04-03` renders `03/04/2026` and
  `04/03/2026`, an instant renders with its time, and the browser fallback
  picks `MDY` for a month-first locale.
- `ProfilePage.test.tsx`: the select shows the saved choice and saves a new
  one.
- Manual: `make db-reset`, set each format on the profile page, and confirm
  the run page, the inventory list, the admin pages and a downloaded
  `lines.csv` all switch together.

## Non-goals and open questions

- Number formats (decimal and thousands separators) follow the browser as
  before. A later spec may tie them to the same preference.
- No organization or platform default; the preference is personal.
- The QA drivers and the help centre still quote ISO dates and screenshots
  made before this spec. They are updated in a follow-up, where the browser
  driver pins the tester's preference so its expectations hold.
- The CSV columns that vary by downloader are the open tension with spec
  07.5's "nothing that varies between downloads". If verifier re-performance
  needs byte-identical files, the alternative is a second, ISO-only download.
