# 01.9: Password change and reset

- **Status**: Approved (the owner pre-approved this spec on 2026-09-29)
- **Protocol**: none directly; Corporate Standard chapter 7 (inventory quality
  management) relies on knowing who acted, which needs accounts their holders
  control, and ISO 14064-1 section 8 (records)
- **Owner**: Michael Takrama
- **Created**: 2026-09-29
- **Modules**: `user` (endpoints, tokens, history, sessions), `mail` (two
  emails), `shared` (security configuration), `src/features/auth`,
  `src/features/profile`, `src/features/admin`

## Problem

CarbonOS has no way to change or reset a password. Spec 01 listed password
reset and change-own-password as non-goals: the password an account has is
the one set from the approval link (spec 01.1) or the temporary one an
administrator typed when creating the account, and the only way to replace
it is the `make admin` command on a machine with database access. A person
who forgets their password has to ask a platform administrator, who has no
way to help from the product. A temporary password handed over in chat stays
the password forever. The help review of 2026-09-28 (triage row 2) recorded
the gap as an owner's decision.

## Behavior

### Change your own password

- The profile page carries a **Change password** section: **Current
  password**, **New password**, **Confirm new password**, the rule "At least
  12 characters, with a letter and a digit." (spec 01.2,
  `PasswordPolicy.RULE`) and the button **Change password**.
- Given a signed-in user, when the current password is wrong, then the change
  is refused with 422 and "The current password is not correct." on the
  **Current password** field. The session is not touched: a wrong current
  password is never a 401, because the app reads a 401 as signed out.
- A new password that breaks the rule is refused with the rule on **New
  password**; a new password equal to the current one is refused with
  "Choose a password different from your current one."; a confirmation that
  differs is refused in the page with "Passwords do not match." before any
  request.
- When the change succeeds, the session that made it stays signed in and
  **every other session of the account ends**; its next request gets the
  same 401 as a missing session. The page shows the toast "Password changed.
  Your other sessions are signed out."
- Five change attempts per account per 15 minutes; the sixth is 429 "Too many
  attempts to change the password. Try again in 15 minutes." This keeps a
  borrowed session from guessing the current password.

### Forgot your password

- The sign-in page links **Forgot your password?** to a page **Reset your
  password** with one field, **Email**, and the button **Send reset link**.
- The answer never reveals whether an account exists. The endpoint answers
  202 with no body for every well-formed address. The page then reads "If
  *email* belongs to an active CarbonOS account, a reset link is on its way.
  The link is valid for 1 hour and works once."
- Only an **ACTIVE** account gets an email. An unknown address, a pending
  account (spec 01.2, which still has its approval link) and a disabled one
  get nothing.
- The email "Reset your CarbonOS password" carries a link to
  `/reset-password?token=…`. The link is **valid for 1 hour** and works
  **once**. Each request issues a new link; earlier open links stay valid
  until their hour ends or until any link of the account sets a password.
- The link opens **Choose a new password**: "Choose a new password for
  *email*." with **New password**, **Confirm password** and **Set new
  password**. On success every session of the account ends, and the page
  sends the holder to sign in, which reads "Your password is reset. Sign in
  with your new password." The reset does not sign the holder in: they prove
  the new password once, and a link that leaked opens no session by itself.
- A link that opens nothing is refused with a sentence of its own, followed
  in the page by "Ask for a new link and use the latest email." and the
  button **Ask for a new link**:
  - an unknown token (or no token): 404 "This reset link is not valid.";
  - a used token, or one voided because another link of the account set a
    password: 410 "This reset link has already been used.";
  - an expired token: 410 "This reset link has expired. Reset links are valid
    for 1 hour."
  Telling used from expired says nothing about accounts: only the holder of
  a real link can reach either.
- **Rate limits**, counted in memory in fixed 15-minute windows (the pattern
  of the help centre's limiter, spec 09): 3 requests per email address and 10
  per client address. Both counters move on every request, whether the
  address has an account or not, so a refusal is no signal either. Past a
  limit: 429 with `Retry-After: 900` and "Too many password reset requests.
  Try again in 15 minutes." One backend instance per environment makes an
  in-memory count enough; a restart forgets the counts.

### An administrator resets a user's password

- **Users** offers **Reset password** on each **Active** account. The
  administrator **sends the reset link**; CarbonOS never shows or sets a
  password for them. This is the safer choice: no password passes through
  the administrator or a chat, and only the mailbox owner can use the link.
  The temporary password at account creation stays as it is (spec 01).
- The dialog **Reset the password of *name*?** reads "CarbonOS emails *email*
  a link to choose a new password. The link is valid for 1 hour and works
  once. The current password keeps working until the link is used." with
  **Cancel** and **Send reset link**. Success shows "Reset link sent to
  *email*."
- The email is the same as the self-service one, except that it reads "A
  CarbonOS administrator sent you this link" in place of "Somebody, probably
  you, asked to reset your password". Sending it changes nothing else: the
  current password and the account's sessions stand until the link is used.
- A pending account is refused with 409 "This account has not set its first
  password yet; the link in its approval email still works."; a disabled one
  with 409 "Enable the account before sending a password reset link." A
  member gets 403, as for all of `/api/admin/**`.

### History and notice

- User events are recorded today only as the Modulith event registry's
  delivery log (`event_publication`, for events with a listener) and, for
  access decisions, in `access_requests` (`decided_by`, `decided_at`).
  Neither is an audit trail of an account, and `ghg_audit_events` needs an
  organization. Every change and reset is therefore recorded in a new
  append-only table, `user_security_events`, owned by the `user` module, for
  the same reason spec 01.5 gave platform settings their own change table:
  - `PASSWORD_CHANGED` (actor: the account holder),
  - `PASSWORD_RESET_REQUESTED` (actor: "anonymous (sign-in page)", recorded
    only for an ACTIVE account, so the table never lists unknown addresses),
  - `PASSWORD_RESET_SENT_BY_ADMIN` (actor: the administrator, id and email),
  - `PASSWORD_RESET_COMPLETED` (actor: the account holder).
  The row keeps the account's id and email and outlives the account.
- Every new password, by change or by link, emails the account holder "Your
  CarbonOS password was changed", saying when (UTC), how ("from your
  profile" or "with a password reset link"), that the other sessions were
  signed out, and where to reset it if it was not them.

### Sessions

Sessions are the servlet container's in-memory HTTP sessions; the app does
not use Spring Session. Spring Security's in-memory `SessionRegistry`
(`SessionRegistryImpl`, fed by `HttpSessionEventPublisher`) records each
session against the account id when the sign-in endpoints create it (the
sign-in page and the approval link's completion). A new password marks the
account's other sessions expired, and the `ConcurrentSessionFilter` refuses
an expired session on its next request with the 401 problem detail. The
registry and the sessions live in the same memory and a restart forgets both,
so they cannot disagree. The number of sessions per account is not capped.

## API

- `PUT /api/profile/password` (signed in, CSRF) takes `{currentPassword,
  newPassword}`: 204; 422 with `errors.currentPassword`, or
  `errors.newPassword` for the rule or the same password; 429 past the limit.
- `POST /api/auth/password-reset` (public, CSRF) takes `{email}`: 202 with no
  body whatever the address; 422 for a malformed address; 429 past a limit.
- `GET /api/auth/password-reset/{token}` (public) returns `{email}` for a live
  link; 404 unknown, 410 used or expired.
- `POST /api/auth/password-reset/complete` (public, CSRF) takes `{token,
  password}`: 204; 422 with `errors.password` for the rule; 404 or 410 as
  above.
- `POST /api/admin/users/{id}/password-reset` (administrator, CSRF): 202; 404
  for no such user; 409 pending or disabled.

The security configuration permits exactly the three public reset endpoints
without a session; CSRF stays on for every POST and PUT.

## Data

`V59__password_reset.sql` creates two tables.

- `password_reset_tokens`: `id`, `user_id` (cascades with the account),
  `token_hash` (SHA-256 of the token, hex, unique), `expires_at`, `used_at`,
  `requested_by` (the administrator, or null), `created_at`. The raw token is
  32 random bytes in hex and exists only in the email; a read of the table
  yields hashes that open nothing. Setting a password marks every open link
  of the account used.
- `user_security_events`: `id`, `user_id`, `user_email`, `action` (checked
  against the four values above), `actor_user_id`, `actor`, `created_at`. No
  foreign key, so the row outlives the account.

## Events

- `PasswordResetRequested(userId, email, displayName, token, validFor,
  sentByAdministrator)`, published by `user`, consumed by `mail`. It carries
  the raw token to the mail module, so the event registry stores it while the
  email is sent. A scheduled sweep in `user` deletes the completed
  publications of this event every minute; an unsent one stays for the retry,
  and its link dies with its hour anyway.
- `PasswordChanged(userId, email, displayName, how, at)`, published by
  `user`, consumed by `mail` for the notice.

## Non-goals and open questions

- No page lists `user_security_events`; it is read from the database for
  now. An account's security history in the administration console is a
  later spec.
- No forced change of a temporary password at first sign-in, and no password
  expiry or history of earlier passwords.
- Changing the email of an account stays a non-goal (spec 01).
- An administrator cannot set a password for someone; the link is the only
  way, by decision.
- The rate limits and the session registry are per backend instance; running
  more than one instance needs a shared store for both (and for the help
  centre's limiter).
