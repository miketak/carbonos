# 02.10: Retiring the shared factor library

- **Status**: Implemented (2026-09-16)
- **Protocol**: Chapter 6 (factors appropriate to the source), Chapter 7
  (transparency: the inventory says what it was calculated with), Chapter 9
  (the source of each factor is reported), ISO 14064-1 (the basis of every
  quantification is stated and traceable)
- **Owner**: Michael Takrama
- **Created**: 2026-09-16
- **Modules**: `ghg` (`EmissionFactor`, `EmissionFactorSearch`, `GhgService`,
  `EmissionFactorController`), `src/features/ghg` (emission factors page, the
  classification picker)

## Problem

Alongside the importable packs, the product shipped a **shared library**: rows
of `ghg_emission_factors` owned by no organization, visible to every one of
them, read-only, and seeded by migrations rather than imported. Spec 02.9 left
fourteen of them.

They were the wrong thing to keep. They predate the catalogue, so they are a
different vintage from the packs that supersede them: the library's diesel row
is DESNZ **2025** rounded to 2.660 while `defra-2026` carries the published
2.66155, and the library's Ghana grid row is an Ecoriv secondary estimate of
0.441 with no published derivation, while the `ghana` pack carries Ember's
0.468809 for data year 2024. Nothing merges across the two tiers (spec 02.3
merges within an organization only), so an organization that imported a pack
held both rows, with the same name, a different figure and no rule saying which
to use. Chapter 7 asks an inventory to be transparent about the factors it
rests on, and "whichever of these two the preparer happened to pick" is not
that.

The tier also cost a distinction the product no longer needs: a `FactorTier`
enum, a `tier` query parameter, a second endpoint, and a two-group picker.

## Behavior

- **An organization starts with no factors.** Nothing is seeded. The emission
  factors page shows the two pack cards and an empty table until the
  organization imports `defra-2026`, the `ghana` pack, or both, or enters a
  factor by hand. That import is the act that establishes the baseline the
  company accounts on, and it is recorded: the edition, its applies-from date
  and its citation travel with every row (specs 02.5 and 02.6).
- **Every factor belongs to an organization.** There is no tier and no
  read-only row. `ghg_emission_factors.organization_id` is `NOT NULL`, so a
  tenant-visible row with no owner cannot be written again.
- **The picker is one list.** The "This organization" and "Shared library"
  headings are gone, because everything the picker offers is the
  organization's own. Ordering, paging, search and the filters are unchanged.
- **Nothing else about a factor changes.** Provenance, vintage, validity,
  approval, pack tags, versioning and the gates all behave as specs 02.1, 02.3,
  02.5 and 02.6 describe them.

Given a new organization: when a preparer opens Emission factors, then the
table is empty and the two pack cards are offered. When they import
`defra-2026`, then they hold 1,868 factors, every one citing DESNZ 2026 with
its own row identifier, and the picker offers them.

Given a preparer classifying grid electricity at a Ghanaian facility: when the
organization has imported the `ghana` pack, then the facility's grid region
suggests the pack's row for the data year (spec 03.4). Until a pack is
imported, nothing is suggested, because nothing is held.

## API

- **Removed**: `GET /ghg/emission-factors`, which returned the shared library.
- **Removed**: the `tier` query parameter of
  `GET /ghg/organizations/{id}/emission-factors`, and the `FactorTier` enum
  behind it. The endpoint returns the organization's factors, which is all
  there are.
- Everything else keeps its shape. `EmissionFactorResponse.organizationId` is
  now never null.

## Data

One migration, `V51__retire_the_shared_factor_library.sql`.

1. It refuses, as `V50` does, if a run line cites a factor it would remove: a
   run line snapshots the factor's name, unit and value and holds no foreign
   key, so nothing in the database would otherwise stop a published report
   pointing at a factor that no longer exists.
2. Assignments release the factor (a classification is working state, and the
   record reads as unclassified again, which is what it is); upstream rules
   that reference one are deleted.
3. The fourteen rows with no `organization_id` are deleted.
4. `ghg_emission_factors.organization_id` becomes `NOT NULL`.

`ghg_densities` keeps its own shared tier (spec 02.2). A typical density is a
physical property of a material, not a factor a company accounts with, so
nothing here touches it.

## Verification

- `GhgApiIntegrationTests` covers a new organization holding no factors, the
  organization owning every row it holds, importing a pack to establish the
  baseline, and the Ghana pack's grid row driving the region suggestion of
  spec 03.4.
- The migration was replayed on a copy of a seeded database: 14 rows to 0, the
  column `NOT NULL` afterwards, and the guard refusing a database whose run
  line cited a library factor while leaving the rows untouched.
- Frontend: `EmissionFactorsPage.test.tsx` (the page lists the organization's
  factors and no library card) and `InventoryDetailPage.test.tsx` (the picker
  is one flat list with no tier headings).
- Manual: `docs/qa/002-organization-setup.md` section F.

## Non-goals and open questions

- **A new organization can do nothing until it imports.** That is the point: a
  baseline is chosen, not inherited. Whether onboarding should prompt the
  import rather than leaving an empty table is a UX question this spec leaves
  open.
- **The grid suggestion now depends on a pack that names the country in its
  row identifier.** `FactorPackImportService.gridRegionOf` reads the third
  segment of codes shaped `PUBLISHER:grid:REGION:YEAR`, which the Ghana pack
  satisfies. A future national pack that numbers its rows differently would
  carry no grid region.
- Whether a curated shared set ever returns, authored in the console rather
  than seeded, is left open. It would need the tier back.
